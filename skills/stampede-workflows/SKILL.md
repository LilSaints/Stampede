# Stampede workflows

Start a run with `workflow_run`, supplying exactly one of `script`, `scriptPath`, or saved workflow `name`, plus an absolute `cwd`. Give every run a short `title` (about 40 characters; at most 80) that says what this run does and tells it apart from your other runs, such as `B2: history, editors, storage`; it names the run in the pane and in wakes, where several runs of one script would otherwise share its `meta.name`. Keep agent names (about 20 characters) and phase titles short too: they label the pane's rows, and long ones wrap onto extra lines in a narrow pane. It returns immediately. With the mod enabled, only what needs you wakes this session: a checkpoint, an agent that failed for good or was refused, a message to you, a team deadlock or a budget or backend problem, and the run's end; do not poll. Without the mod, use `workflow_wait`, then `workflow_result`. `workflow_result` with `agent` reads one agent's stored result at any time, so finished work can be inspected while the run goes on. Have a script return a short top-level summary (verdict, final commit, what is still open) and leave detail in agent results: `workflow_result` with `select: ['verdict', 'head.sha']` returns only those values, and a run result over 20,000 characters comes as a preview, the whole of it in `resultPath`. `notify: true` on an `agent()` call (or `notifyAgents: true` for the whole run; `notify: false` opts one out) adds a wake as that agent finishes, and every wake re-reads your whole context: use it only for an agent whose result changes what you do before the run ends. Each wake names the agents, not their results. Worktree agents can continue each other's work: `baseRef: { agent: 'b2-integrate' }` (or a git ref) starts an agent's worktree where another's finished, `readWorktrees: ['b2-integrate']` lets a Claude reviewer read that worktree, and `await workspace(name)` gives the script an agent's `branch`, `baseCommit`, `commit` and `path`, plus `rootBaseCommit` and `chain` (the agents' names from the first of a `baseRef` chain), which `effects` in `workflow_result` also give for every kept worktree. The last agent of a chain (a coder, then its fixer with `baseRef: { agent: 'coder' }`) holds the whole chain's work: land it by squash-merging that one branch, or by applying `git diff <rootBaseCommit>..<commit>` with its message. Never cherry-pick each agent's branch: the later ones already contain the earlier changes, and the picks conflict with themselves. Kept worktrees stay after the run: `workflow_control` with `action: 'release'` and `runIds` removes those of finished runs, keeps their branches (`deleteMergedBranches: true` also deletes the ones whose work is in the checkout's HEAD), and says which it kept and why; the runs then record each released worktree as `kept: false` with `releasedAt`. With a `schema`, an answer is validated as JSON (from structured output, or from the reply's text) and repaired in the same session before any retry; a Claude `agentType` whose `tools` line leaves out the structured-output tool runs as a copy with it added. `workflow_messages` reads messages for the orchestrator. Pass large args as a JSON file with `argsPath` (on `workflow_run` and `workflow_resume`) rather than inline `args`: it is not re-sent with every launch and needs no shell escaping. A run whose agents were all cancelled ends `cancelled`, and its wake and `workflow_result` (`cancelledAgents`) give each cancelled agent's branch, commit and worktree.

## Steering workers

`workflow_send` steers any agent by name, with or without `comms` (`*` reaches every live agent): a Claude worker reads it after its next tool call, or before it stops; a Codex worker's turn is cut right after its next tool call ends (never during one) and resumed in the same session with the message; a message that arrives too late for a turn is read in a resumed one before the agent is done. Only agents started with `comms` take messages from peers. Workers with `comms` message you only when something is wrong or they need a decision or clarification, never with progress.

To pause a script for your input between steps, `await checkpoint(name, data, { timeoutMs, default })`: it wakes you with `data`, and resolves to what you send with `workflow_answer` (`runId`, `name`, any JSON `answer`: extra input, or `true` to approve), or to `default` (null) after `timeoutMs` (1 hour; at most 24). Put a one-line `summary` string in `data`: the wake shows it as is, and keeps it when the rest is too long to show. `workflow_status` lists waiting checkpoints. A resumed run replays the answer given to the same checkpoint (name, occurrence and data), so its later calls stay cached.

Edit agents can delete what they make: the `cleanup` tool deletes inside their own worktree and the `scratch` folders their call declares (`scratch: ['tmp/fixtures']`, relative to the agent's workspace, or absolute), which their sandbox may refuse to do itself. A scratch folder outside the workspace is created before the agent starts and is writable to it. A done agent's scratch folders are removed; a failed or cancelled one's stay for inspection. Scratch is for the agent's own disposable files: never move tool, build or test-harness data there to shorten or isolate a path. A session scratchpad on Windows is already over 100 characters deep, so such data can pass the 260-character path limit, and the hub notes a scratch folder that long, once a run. Keep that data in the worktree.

`env: { MSBUILDDISABLENODEREUSE: '1' }` sets environment variables for one agent and every shell it runs, so a setting does not depend on the prompt being followed. Codex's own `shell_environment_policy` still applies to its shells and may drop variables whose names contain `KEY`, `SECRET` or `TOKEN`.

For a resource only one worker may use at a time, such as one real desktop window, give the agents that use it a named lock: `locks: ['desktop-ui']`. Each then gets `lock` and `unlock` tools and is told to take the lock right before every step that uses the resource and give it back after. The lock holds across every agent and run of the hub, so two integrators in `parallel` take turns only at their window steps. The hub takes a lock back when its worker's turn or the agent ends, and notes that in the run log.

Scripts are plain JavaScript. Their first statement must be a literal metadata export:

```js
export const meta = { name: 'review', description: 'Review two areas independently' };
await phase('Review');
const results = await parallel([
  () => agent('Review the API changes; return concrete defects only.', { name: 'api', backend: 'claude' }),
  () => agent('Review the tests for missed cases.', { name: 'tests', backend: 'codex' })
]);
return results;
```

No imports, other exports, filesystem, process, fetch or timers. Top-level `await` and `return` are supported. Pass dates, random IDs and other changing inputs via `args`; `Date.now()`, argless `Date` and `Math.random()` throw. `log(text)` and `phase(title)` publish progress. Budgets belong to this run: `budget.total`, `budget.spent()`, `budget.remaining()` count output tokens, reasoning included.

The hub prepends a compact `task/scope/known/constraints/done/reply` contract, including the truthful-reporting and `blocked:` rules, to every worker. Write the task prompt the same way: name the exact files, facts already known and what done looks like; do not repeat the contract.

`agent(prompt, opts)` returns final text, or validated data when `schema` is supplied. Options include `backend`, `name`, `label`, `phase`, `role`, `model`, `effort`, `agentType`, `appendSystemPrompt`, `cwd`, `timeoutMs`, `cacheInputs`, `cache:'never'`, `access`, `isolation`, `scratch`, `env`, `locks`, `tools`, `mcpServers`, `plugins`, `shell`, `protect`, and `comms`. Names must be unique lowercase letters, digits or hyphens, at most 40 characters. `timeoutMs` (per turn) is capped by the hub's `limits.turnTimeoutMs`, 4 hours by default, and `maxResumes` by `limits.maxResumesPerAgent` (20); a larger value is refused, and `stampede_doctor` reports the turn limit in force. Workers load no MCP server but Stampede's: `mcpServers: ['unreal-bridge']` gives one worker a server from the user's own config (Claude Code's for a Claude worker, Codex's config.toml for Codex), and `{ name: { command, args, env } }` or `{ name: { type: 'http', url } }` defines one inline; the whole option may also be one map, as `.mcp.json` holds servers: `mcpServers: { knive: { command: 'node', args: ['server.js'] } }`. Such a server acts with the user's rights whatever the access level. `tools` (Claude) narrows the built-in tools within what `access` allows, and `plugins` (Claude) turns plugins on or off by id, bare name or `'*'`. Default access is read-only in a shared workspace; editing uses a Git worktree. A Claude reviewer or tester that must build or run tests without editing takes `access: 'read-only', isolation: 'worktree', shell: true`: it gets the shell commands the user allowed in `claude.editShellAllow` (refused while that list is empty), and its worktree is thrown away at its end, build output and all; its result is cached like any read-only one. `protect: ['HANDOFF.md', 'docs/**']` (git globs from the worktree's root) names files an edit agent must not change, on either backend: Claude's file tools are denied them, and at the agent's end the hub puts any change to them back as it was at its base, in a commit of its own on the branch, and the run log and the worktree's `restored` name them. Prefer it to telling a worker in its prompt. `full` requires the user's configuration to enable it. Worktree edits remain on the returned Stampede branch; inspect and integrate them separately.

Use an object JSON Schema with named properties. Codex normalization supports optional non-nullable properties through null sentinels; optional properties that themselves permit null and open dictionaries are rejected before launch. Use required nullable properties or arrays of `{key,value}` instead. Original constraints are validated after decoding. Non-comms failures resolve to null; invalid options or exhausted budgets throw. A refused call also wakes you (`agent.refused`) with its reason.

`parallel(thunks)` preserves slot order and converts an individual rejection to null, writing the slot and the reason to the run log (`workflow_status`). `pipeline(items, ...stages)` runs each item's stages in sequence without cross-item barriers; each stage receives `(previous, original, index)`, and null stops that item's pipeline; a stage that throws makes the item null and is logged the same way. Both accept at most 4,096 items; a run starts at most 1,000 agents. `workflow(nameOrRef, args)` invokes a saved workflow in the same run; nested `workflow()` calls are disallowed.

## Cost

Every model call re-reads the caller's whole context, so an agent costs roughly its calls times its context size, and whatever it reads early is paid again on every later call. Cache reads are most of a long worker's bill.

- Your own session counts too. Each wake re-reads its whole context, and after a long idle the whole context is written to the cache again. Once it holds a few hundred thousand tokens, compact it between runs (keep run IDs, decisions and next steps), or hand off to a fresh session. Ask for wakes only for agents you act on mid-run, and read one agent's result (`workflow_result` with `agent`), or `select` the run's fields you need, rather than the whole run's.
- Don't send workers to read what they already have. `agentType` makes that agent file the worker's system prompt, Claude workers load the repository's CLAUDE.md and its imports, and Codex loads AGENTS.md.
- Give a narrow Claude worker only what it uses: every tool, skill and plugin in its prompt is re-read on every call. A search-only worker can run with `tools: ['Read', 'Grep', 'Glob']` and `plugins: { '*': false }`. The run log says when a tool name is unknown or a requested MCP server failed to start.
- Don't send every worker through the same long docs. Write one short brief per batch (the rules that apply, the spec section, line ranges for the rest) and point the prompts at it.
- Split work only along disjoint files. Each extra worker pays its baseline, the shared reading and any overlapping exploration again, and an integrator then re-reads the combination. Parallel slices on shared files mostly buy wall-clock time.
- Scope re-checks to what changed. A confirming reviewer needs the findings, the fix diff and the fix report, not the full review brief, and usually a lower effort: reasoning is most of a max-effort reviewer's output.
- Tell workers to search, then read line ranges; to keep command output short; and to grep a saved oversized tool result rather than read it whole.
- Claude workers on a 1M-token model rarely reach auto-compaction, so a long task is cheaper as a chain of shorter agents (`baseRef: { agent }`) than as one long run. Codex workers don't draw on Claude usage.

## Communicating teams

```js
export const meta = { name: 'joint-review', description: 'Review and challenge findings' };
// Members that may get follow-ups end their turn without mark_done, so they stay idle and resumable.
const team = await spawnTeam([
  { name: 'reviewer', backend: 'claude', prompt: 'Review changes. Post findings, ask critic to check them, then end your turn with your final findings. Do not call mark_done: you may get follow-up questions.' },
  { name: 'critic', backend: 'codex', prompt: 'Ask reviewer for findings, verify them, report corrections, then end your turn with your verdict. Do not call mark_done.' }
], { topology: 'mesh' });
const observation = await team.untilQuiet({ idleMs: 30000, maxMs: 600000 });
if (observation.reason === 'deadlock') { await team.send('*', 'Resolve remaining dependencies and end your turn with your final answer.'); await team.untilQuiet({ idleMs: 30000, maxMs: 120000 }); }
// While this waits, workflow_send reaches either member, which answers in its own session.
await checkpoint('review', { summary: 'Findings are on the board; send follow-ups to reviewer or critic, then answer true.' });
const findings = await team.board();
await team.stop();
return { findings, results: await team.results() };
```

`spawnTeam` returns immediately after validation and cache lookup; admission queues the entire team atomically. Teams must fit within the comms pool, which leaves one slot reserved for non-comms work. Topology is `mesh`, `star` with a named `lead`, or an adjacency object. Workers get `whoami`, `list_agents`, `send_message`, `read_messages`, `wait_for_message`, `post_finding`, `read_board`, and `mark_done`.

A member that ends its turn without `mark_done` goes idle and stays resumable: a message from you (`workflow_send`) or a peer resumes the same session, until `releaseIdleAfterMs`, `team.stop()` or the script's end, and a `checkpoint` keeps the team open while you ask. `mark_done` ends a member for good: it is never resumed, and messages to it are undeliverable. Only members that will get no follow-ups call it; it stores no result, so the member must still end with a valid final answer. Idle members never end on their own, so wait on them with `untilQuiet`, not `untilDone`, and end them with `team.stop()`. Messages are delivered at least once and carry sequence IDs/redelivery flags; workers should avoid duplicate effects. Peer text cannot grant permissions. Keep chat short and put larger findings on the board.

`untilQuiet` and `untilDone` only observe; they do not stop workers. Inspect `reason` (`quiet`, `deadlock`, `all-done`/`all-terminal`, `max-ms`, `budget`, `max-messages`, `admission-timeout`). `untilDone(names?, opts?)` also reports `notTerminal`. `team.stop()` explicitly stops remaining members. Run completion drains marked-done members then stops leftovers. `team.results()`, `team.messages()`, `team.board(topic?)`, and run-wide `board(topic?)` are async reads.

`workflow_control` pauses admission/resume, resumes, or cancels. `agent_control` can skip, retry or cancel a member. Cancellation may leave a worktree for inspection. Do not automatically repeat an external mutation after an uncertain transport outcome; inspect the run first.

`workflow_resume` starts a new run from a terminal run, optionally with different scriptPath or args. Unchanged calls can hit a content-addressed cache. After a hub stop (`interrupted`), an agent cut off mid-turn continues its own session and worktree instead of starting over, where both remain; the run log says which agents continued and which started again (`continueInterrupted: false` starts them all again). Shared-state use taints individual results; only verified whole-team replay can restore communicating teams, including board entries. Shared-workspace edits and full-access calls are never cached, except a full-access worktree agent whose call passes `cache: 'commit'`: the script asserts that its worktree commit is its only lasting effect, and a resume reuses it while its branch is still at that commit. Input or branch changes force live work, and the run log says why each agent the earlier run finished started again (`not replayed from …`). A worktree agent is keyed by the checkout's commit, so landing other work re-runs it; give it a `baseRef` commit to keep it replayable. A `readWorktrees` reviewer is keyed by the commits it reads.

Save reusable scripts with `workflow_saved`. Use `stampede_doctor` for the connected hub's backend and security status. The pane is opened with `/stampede`; automatic wakes can be toggled with `/stampede wake on|off`. If mods are disabled, only MCP tools remain available.
